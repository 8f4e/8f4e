# @8f4e/runtime-linux

A standalone C++20 Linux host for compiled 8f4e instruments. It embeds Wasmtime and uses ALSA for stereo audio
output and one MIDI 1.0 input. It loads WebAssembly and accepts numeric audio-buffer byte addresses. Memory limits
come directly from the WASM import; the runtime needs no memory-map file, JSON parser, editor or Node.js.

## Build on Linux

Use a 64-bit Linux installation, including Raspberry Pi OS on a Pi 5. Install the build dependencies:

```sh
sudo apt-get install build-essential cmake libasound2-dev ca-certificates
```

From the repository root:

```sh
npx nx run @8f4e/runtime-linux:build
```

The executable is `packages/runtime-linux/dist/8f4e-runtime`. CMake downloads the Wasmtime 50.0.1 C API distribution
for ARM64 or x86-64 and verifies its SHA-256 digest. To use an already extracted distribution, configure CMake with
`-DWASMTIME_ROOT=/path/to/wasmtime-c-api`. Wasmtime is linked statically; ALSA remains a system dependency.

Without the JavaScript workspace tooling, the native package can also be built directly:

```sh
cmake -S packages/runtime-linux -B packages/runtime-linux/dist/build -DCMAKE_BUILD_TYPE=Release
cmake --build packages/runtime-linux/dist/build --parallel 2
```

## Compile an instrument

Build the CLI and export the DX7 project on the development computer:

```sh
npx nx run @8f4e/cli:build
node packages/cli/bin/cli.js compile packages/examples/src/projects/midi/dx7Algorithm5EightVoices.8f4e \
  --wasm-output /tmp/dx7.wasm \
  --memory-output /tmp/dx7.memory.json
```

The JSON is used only by the separate [runtime-command tool](../../tools/runtime-command/README.md) on the
development computer. That tool resolves symbols in the compiler memory map and prints a shell command containing
numeric byte addresses and the declared audio-buffer size. Generate a Pisound launch command with:

```sh
node tools/runtime-command/src/cli.mjs dx7.wasm /tmp/dx7.memory.json \
  --runtime ./8f4e-runtime -- \
  --audio-device plughw:CARD=pisound --midi-device hw:CARD=pisound --sample-rate 48000
```

Copy `/tmp/dx7.wasm` to the Linux machine as `dx7.wasm`, alongside the executable, and run the printed command there.
Only the WASM file and executable are needed on the target. Regenerate the command whenever recompilation changes
the memory layout. For separate buffers, give the command tool `--left output:left --right output:right` before `--`;
full nested references such as `synth/voice/output:left` are supported.

The compiler always emits shared memory. This host enables Wasmtime's shared-memory support and imports the
memory declared by the WASM file. MIDI and audio still execute sequentially in one instance on one thread;
shared memory does not introduce concurrent playback or automatic synchronization.

## Run with Pisound

Use `aplay -L` to find PCM device names and `amidi -l` to find raw MIDI devices (`alsa-utils` supplies both commands).
For a Pisound card named `pisound` and an instrument whose 128-sample left/right buffers start at byte offsets
0 and 512 respectively, the numeric command is:

```sh
./8f4e-runtime instrument.wasm --left 0 --right 512 --buffer-size 128 \
  --audio-device plughw:CARD=pisound \
  --midi-device hw:CARD=pisound \
  --sample-rate 48000
```

The ALSA `plughw` device converts the runtime's stereo float32 stream into the card's supported hardware format.
`--left` is required and accepts a decimal byte offset, including zero. `--right` defaults to the left address for
dual-mono output. Audio samples are little-endian float32 values. `--buffer-size` defaults to 128 and must equal
the number of samples generated by each call to the WASM block function. Both buffer ranges must fit in the imported
memory. `--sample-rate` must match the project's compiled `SAMPLE_RATE` constant; it does not retune or recompile
the instrument. Use the generated command for the actual DX7 buffer address.

The host calls `initDefaults()` once, then invokes the exported `buffer()` function for every audio block. It reads
MIDI in nonblocking mode between blocks and invokes `onMidiEvent(i32 status, i32 data1, i32 data2)`. All functions
run on the same thread and return no values. `--entry` and `--midi-callback` override those export names. MIDI input
is disabled when `--midi-device` is omitted, and no MIDI export is then required. Running status, short messages,
split reads, and interleaved realtime messages are supported; SysEx payloads are ignored.

Output gain defaults to `0.25`; use `--gain` to change it. Samples are clipped to `[-1, 1]` after gain. The host
preallocates its audio buffer and prepares WASM before opening devices. ALSA paces the blocking audio writes,
including partial writes and underrun/suspend recovery. Ctrl-C and SIGTERM stop playback and close the devices.
MIDI timing is quantized to block boundaries. This first version supplies audio output and MIDI input only;
audio input, MIDI output, hot reload, and sample-accurate MIDI scheduling are outside its scope.

## Validate

On Linux with the build dependencies installed:

```sh
npx nx run @8f4e/runtime-linux:test
```

This compiles a local `.8f4e` fixture through the real CLI, tests MIDI parsing and exported callbacks, verifies
numeric memory routing, stereo/mono output and gain, and runs a launch command generated by the separate tool against
ALSA's `null` PCM device. It also checks invalid numeric buffer arguments. No sound card or MIDI interface is needed.
For a bounded smoke test, add `--audio-device null --blocks 100` to the numeric launch command.

The **Linux runtime / Test** workflow runs native tests on Linux x86-64 and ARM64. Web test/release workflows exclude
the native runtime and its command tool and do not install Linux audio development dependencies.

These checks do not measure hardware latency or prove glitch-free playback on a Pi. Test the actual interface and
polyphony before using it for a performance.

## Release

Manually run **Linux runtime / Release** from `main`. It builds and tests native x86-64 and ARM64 executables, then
publishes compressed archives in a GitHub release tagged `@8f4e/runtime-linux@<version>`. The version comes from this
package's `package.json`; update it and the root lockfile in a PR before the next release. Releasing an existing tag
fails instead of replacing its assets. The release does not version web packages, collect web metrics, or deploy sites.
The normal web release excludes this package from Nx versioning and tests.
